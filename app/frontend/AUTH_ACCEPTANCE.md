### 实现与安全边界

- 原登录入口、原JWT链路与旧项目owner不变。独立账号通过现有users表创建`demo:`前缀随机主体，新增的三张表仅为凭据、会话及限流扩展，不建立第二用户表、不按相同邮箱关联原账号。
- `POST /api/v1/demo-auth/register` / `login`接受email/password；密码10–128字符，PBKDF2-HMAC-SHA256 600000轮与随机盐，数据库只存密码摘要。邮箱规范化并用PostgreSQL事务级邮箱锁序列化注册。角色固定user。
- 注册与登录建立一天有效的随机会话；服务端只存SHA256会话摘要，浏览器使用Secure、HttpOnly、SameSite=Lax Cookie。不将密码或会话令牌放入localStorage、查询参数或返回JSON。
- `GET /me`真实查询会话和用户；`POST /logout`服务端删除当前会话。注册后前端再次me核验才挂载工作台。localStorage只保存非敏感的demo/original模式；独立模式过期或退出不自动回退到平台身份。
- 自定义SDK请求携带`X-Demo-Auth: 1`并启用Cookie。鉴权依赖在该模式优先核验Cookie，即使SDK附带平台Bearer也不混用。旧入口仍走原SDK认证。
- 认证接口拒绝跨站浏览器请求及缺少专用头的请求；输入流限制4096字节，验证错误只返回固定提示、不回显密码。SQL错误回滚并返回固定503，不记录SQL异常参数。
- 密码运算前通过数据库原子计数限流：每邮箱15分钟10次，全局15分钟200次；超限429。此处没有IP级策略，全局限流可能影响多个用户，定位为Demo而非大规模公共认证服务。
- 凭据、会话与限流实体的自动CRUD路由全部关闭。所有项目、消息、文件、生成及预检继续使用现有服务端父资源归属校验。
- 本Demo不验证邮箱、不发送邮件、不提供密码找回，界面与API明确email_verified=false。并未实现或声称官方原生注册能力。
- test01不迁移、改名、重置或删除，新账号不能接管它。未修改受保护core/models/main/lambda_handler/只读AuthCallback/系统预览配置，生成代码仍不执行。

### 身份结论与准确接口

**当前是“上游平台认证主体 + Demo应用会话”，不是已证实的独立Demo注册账号体系。**

代码依据：OIDC回调把已校验ID token的sub传给 `get_or_create_user(platform_sub=...)`；原生User.id沿用platform_sub；应用JWT的sub又取User.id。平台token/exchange分支先向上游核验平台令牌，再使用返回user_id。项目归属取经应用JWT验证的current_user.id。

因此应用确有自己的用户记录与JWT，但账号主体沿用上游，不生成独立的Demo密码身份。仅凭函数名不能确认托管服务面向哪些用户开放；当前实际真人登录采用哪个分支、当前issuer所服务的租户范围仍未实测。不能把平台已登录状态直接视为Demo已登录。

| 应用实际接口 | 方法 | 作用 |
|---|---|---|
| `/api/v1/auth/login` | GET | 创建OIDC state/nonce/PKCE并重定向上游authorize |
| `/api/v1/auth/callback` | GET | 校验回调、换取上游令牌、验证身份、映射原生用户、签发应用JWT |
| `/api/v1/auth/token/exchange` | POST | 核验平台令牌后签发应用JWT；本轮不调用 |
| `/api/v1/auth/me` | GET | 用原生认证依赖返回应用当前用户 |
| `/api/v1/auth/logout` | GET | 返回官方退出地址；路由本身不执行JWT撤销 |

上游地址在代码中由 `oidc_issuer_url` 拼接 `/authorize`、`/token`、`/.well-known/jwks.json`、`/platform/tokens/verify` 和 `/logout`。这些是代码构造规则，不是经过浏览器确认的注册页面URL。本轮没有读取运行issuer值或输出带认证参数的地址。安全的已知登录入口仍是应用按钮→SDK toLogin，而不是手工拼接注册链接。

### 平台身份与应用身份的区别（代码检查）

- 平台登录身份由上游 OIDC/平台认证服务证明。应用不能把“已登录 Atoms 网页”或前端布尔值当成已登录 Demo。
- Demo 的受保护接口使用自己的应用 Bearer JWT，经 `get_current_user` 验签和有效期检查后取得 `sub`、角色等身份信息。应用会话与平台会话不是同一个令牌或同一个退出保证。
- 官方 OIDC 路径：`/api/v1/auth/login` 创建一次性 state、nonce 和 PKCE → 托管授权页面 → 服务端 `/api/v1/auth/callback` 换取令牌并校验签名、issuer、audience、nonce → `get_or_create_user` 按上游 sub 查找/创建原生用户记录 → 签发应用令牌 → 原生只读前端回调调用 `client.auth.login()`。
- 用户表记录的创建发生在上游身份已验证之后，只是映射认证主体，不是独立密码注册。应用用户 ID 沿用上游 sub；没有自建密码表或另一个账号体系。
- 另有 `/api/v1/auth/token/exchange`：服务端向上游核验平台令牌后使用核验返回的 user_id 签发应用令牌。不能用这个接口绕过上游创建测试用户，本轮也未调用它。
- 项目列表按当前已认证用户 ID 查询，项目创建由服务端设置 user_id；修改、文件、消息及生成接口核验父项目归属。管理员角色也不会绕过这些工作台归属条件。
- AuthGate 初始化只调用一次 `me()`；核验期间不挂载工作台，401 显示登录，非401显示核验失败；没有因为数据库或模型失败自动改成匿名。

原生 SDK 正式指南只列出 `me`、`toLogin`、`login`、`logout` 四个认证方法，明确没有 `signUp` 等方法。现有路由也没有 signup、邮箱密码登录、邮箱验证、密码重置或管理员创建认证用户的端点。**这证明当前应用没有可直接使用的独立注册契约；不能证明托管认证产品全局不存在注册能力。**

## 已确认的代码链路

1. AuthGate 初始化调用原生 `client.auth.me()`；实际 SDK 实现发送 `/api/v1/auth/me` 请求，不是仅查看本地布尔值。认证加载完成前不挂载工作台。认证成功才调用项目读取；401 显示登录入口，其他失败显示无法验证。

4. 当前 SDK 0.0.77 的 logout 实现：先清理应用令牌并设置 SDK 退出标记，再请求 `/api/v1/auth/logout`，请求成功后跳转首页。应用未自行猜测或删除 SDK 存储键，没有清空其他应用 localStorage。
5. 当前平台后端 `/api/v1/auth/logout` 返回官方登出地址；SDK 实际跳转首页，不访问这个返回地址。该后端接口也没有在当前代码中执行应用 JWT 撤销。因此**应用会话清理不能等同于官方 SSO 会话退出或旧令牌立即失效**，本轮不宣称这些保证。SDK 在接口失败前可能已清理本地令牌，界面应报告失败而非认证服务成功。
